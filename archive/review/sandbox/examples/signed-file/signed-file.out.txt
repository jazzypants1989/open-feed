§2.1 — three parts, and nothing else

  body       {"n":1,"at":"2026-07-04T10:15:00Z","text":"the peonies came back"}
  separator  one \n byte
  signature  Pe6ZO_mwGsToFUaNh1sRuPI7kTastKn7qJ3KpXyPBupKLLJzuoZiAnfwUbXTxnULHkLkqevKxmU3q3xPj1ehDQ

  66 body bytes + 1 + 86 signature characters = 153 bytes on the wire.
  That is Appendix B.6 of the spec, byte for byte.

§2.1 — the signature says who, and nothing else does

  verified under  pukq6VMQM9Sbp4ae71bJjcKbLLpFuWi47cDS60xH7CY  (alice's anchor key)
  under mum       null   — not a file, as far as mum's key is concerned

  A file is not "from alice" because of where it was served or what it claims.

§2.1 — the body carries no raw newline, so "the last line" and "the line after the body" agree

  text            "line one\nline two"
  body bytes      {"n":2,"text":"line one\nline two"}
  raw \n in body? false   the serializer escaped it

§2.2 — the address is the hash of the body

  SHA-256(body)   hURWhg38Wl033FFA1HeqvE5bZQiPnEOREVbvIJij9kY
  SHA-256(file)   q7ifEvy4GKl49jG2KTNSIAGFkzcH-3TPKVRdaoiRf7o   not an address of anything

  the same body signed by mum instead:
  file bytes      differ (Pe6ZO_... becomes Kbj7k0...)
  address         hURWhg38Wl033FFA1HeqvE5bZQiPnEOREVbvIJij9kY   identical

  Some standard libraries randomize Ed25519, so two honest signings of one body differ.
  Hashing the whole file would make the address depend on which library signed it.
