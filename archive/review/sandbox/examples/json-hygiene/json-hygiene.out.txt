§2.4 — four bodies `JSON.parse` accepts

  a duplicate member  — which post is this?
    body          {"n":1,"n":2}
    JSON.parse    {"n":2}
    §2.4 parser   rejected: duplicate member name "n"

  __proto__ as a member  — a member that is not data
    body          {"__proto__":{"n":9}}
    JSON.parse    {"__proto__":{"n":9}}
    §2.4 parser   rejected: reserved member name "__proto__"

  an integer past 2^53  — a number that is not the number
    body          {"n":9007199254740993}
    JSON.parse    {"n":9007199254740992}
    §2.4 parser   rejected: integer 9007199254740993 outside ±(2^53 − 1)

  a lone surrogate  — a string that is not the string
    body          {"text":"\ud800"}
    JSON.parse    {"text":"\ud800"}
    §2.4 parser   rejected: unpaired surrogate in string

  Nothing in JSON says which duplicate wins — this parser keeps the last, others keep
  the first — so one signed body can be post 1 to you and post 2 to me. The integer is
  worse: no reader is even given the choice.

  served 9007199254740993 → JSON.parse gives 9007199254740992, silently, and a post
  number is what the index admits and what a reply targets (§4.1, §5.1).

§2.4 — the lone surrogate, in bytes

  parsed string   1 UTF-16 unit, 0xd800, half of a pair
  re-encoded      efbfbd  (U+FFFD — the replacement character)
  Two readers that display, index, or re-encode it hold different text.

§2.4 — the producer half: a signer refuses to emit what a reader would reject

  __proto__             reserved member name "__proto__"
  an integer past 2^53  integer 9007199254740992 outside ±(2^53 − 1)
  a lone surrogate      unpaired surrogate in string

  A duplicate member has no fourth line here: a JavaScript object cannot hold one, and
  no serializer emits one. That is the shape of all four — unreachable by accident,
  reachable on purpose, which is why the reader checks anyway.

§2.4 — why `__proto__` is called out separately

  JSON.parse gives an own member named __proto__, harmless until something copies it:
  Object.assign({}, parsed).n   9   — inherited, with no own member named n
  own member?                   false
  §2.4 parser                   rejected: reserved member name "__proto__"
  A reader that does not reject it MUST at least parse into an object it does not
  inherit from — Object.create(null) — so a member never arrives from a prototype.

§2.4 — and everything else is ordinary JSON

  escaped   {"n":9007199254740991,"text":"the peonies \ud83d\udc90 came back"}
  literal   {"n":9007199254740991,"text":"the peonies 💐 came back"}
  same object: true   same file: false — §2.3 signs the bytes, not the object

Every line above is asserted.
