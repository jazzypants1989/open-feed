§6.4 — bucket(n, floor) is the greater of floor and the next power of two at or above n

  bucket(  1,   8)  =    8
  bucket(  6,   8)  =    8
  bucket(  8,   8)  =    8
  bucket(  9,   8)  =   16
  bucket( 17,   8)  =   32
  bucket(100, 512)  =  512
  bucket(512, 512)  =  512
  bucket(513, 512)  = 1024

  8 is a power of two and it is the floor, so it stays 8; 9 is one over, so it doubles.
  Anything below the floor is the floor. The recommended floors are 8 slots and 512 bytes.

§6.4 — slots are padded to bucket(slot count, slot floor) with dummies

  a direct message  2 recipients + 6 dummies = 8 slots
  the whole family  6 recipients + 2 dummies = 8 slots

  Two recipients and six come out of the envelope at the same width.

§6.4 — a dummy MUST be indistinguishable in width from a real slot

  every slot, real or dummy   8/48 bytes  (tag / wrapped content key)
  as base64url in the file    11 / 64 characters
  distinct widths, 16 slots   1

  Mum scans, finds her own, and opens it: "I am leaving him on Friday"
  What the padding tells her about the rest: nothing. She sees 8 slots and learns the
  audience — 2 people — from §6.5's list inside, not by counting.

§6.4 — and it MUST NOT be derived from anything a recipient holds

  Mum holds the content key: it is what her slot wraps (§6.1). Ask how many of the
  eight slots she can regenerate for herself:

  random bytes, as §6.4 requires   0 of 8   she can subtract nothing
  derived from the content key     6 of 8   8 − 6 = 2: she has counted the true audience
  derived from epk, which is public in the post: 6 of 8 for the host as well.

  Padding that anyone can recompute is not padding; it is a longer file.

§6.4 — the body is padded to bucket(length + 2, body floor)

  what                          plain   +2   bucket
  a direct message                332  334      512
  the same to mum and sis         471  473      512
  the last plaintext that fits    510  512      512
  one byte more                   511  513     1024

  The 2 is §6.1's two-byte big-endian length prefix, which is padded along with the
  plaintext — so 510 bytes of content still fits the 512-byte bucket and 511 does not.

§6.4 — a message to one person is the same size as a message to the family

  SHOULD: a floor of 8 slots and 512 bytes
    post 5, to mum alone        1574 bytes   8 slots, 512-byte body
    post 6, to mum and sis      1574 bytes   8 slots, 512-byte body
    the same file size: true

  the floor off, power of two alone
    post 5, to mum alone        1076 bytes   2 slots
    post 6, to mum and sis      1242 bytes   4 slots
    the same file size: false — the host reads the audience size off the file size.

  The floor hides the audience size for as long as §6.5's audience list fits under it:
    post 7, to five others      2257 bytes   8 slots, 1024-byte body
    the audience list alone is 847 bytes, so this body lands in the next bucket.

§6.4 — it is a SHOULD and not a MUST, and the reason is a number

  a direct message with the floor      1574 bytes
  the same message without it          1076 bytes
  what the floor costs                  498 bytes — six dummy slots, at 83 bytes each

  A minimal implementation that skips it is still conformant: nothing about opening the
  envelope depends on the padding, and a reader cannot tell whether a publisher paid.

§6.4 — what padding does not hide

  the host holds no key, and reads off the file anyway:
    that an encrypted post exists   the "encrypted" member is right there
    when it appeared                2026-08-18T21:40:00Z
    which bucket it is in           512-byte body, 8 slots
    who fetched it, and when        not in the file at all — it is in his logs
  and cannot read: null — the text, the audience, one recipient or six.

  Padding takes size away from him. It leaves existence, timing, frequency, and fetches (§13.3).

Every line above is asserted.
