§8 — the whole interface, on one screen

  PUT /<name>/profile        If-Match: <etag>   → 200 | 412
  PUT /<name>/index          If-Match: <etag>   → 200 | 412
  PUT /<name>/posts/<n>                         → 201 | 200 (reclaimed) | 409
  PUT /<name>/media/<hash>                      → 201 | 200 (replaced)  | 409
  PUT /<name>/feed.json | feed.xml | index.html  If-Match: <etag>  → 200 | 412   (views, §11)
  GET any of the above                          → 200 | 404

  There is no account, no token, and no session: the request is the signed file. Anyone's client
  can write to anyone's hub — a security property, not a convenience, because a hub that ships
  the app is a hub that can take the key. Alice claims a name with three requests:

  PUT /alice/profile                             → 200
  GET /alice/index                               → 404
  PUT /alice/index                               → 200

  Nothing else was sent. No header this hub reads says who alice is; her signature does.

§8.1 — the two overwritable files move only from the version you read

  PUT /alice/posts/1                             → 201
  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "5RgsaBeT…" → 200
  PUT /alice/index                               → 412   no If-Match at all, on a file that exists
  PUT /alice/index         If-Match: "stale"     → 412   a tag that is not the one being served
  PUT /alice/feed.json                           → 200   a view is unsigned and rides the same rule (§11)

  The 412 hands back the tag the hub is serving: "PfbF_ERC…"  A writer reads that from the ETag header
  and never computes it: it is strong, opaque, and compared byte for byte. Two devices hold it now.

  PUT /alice/posts/2                             → 201   the phone gets there first
  PUT /alice/index         If-Match: "PfbF_ERC…" → 200
  PUT /alice/posts/3                             → 201
  PUT /alice/index         If-Match: "PfbF_ERC…" → 412   the laptop lost the race
  PUT /alice/index         If-Match: "1MhdFwWG…" → 200   the naive retry: its own entries, the hub's new tag

  A pinned reader now says  ok ["withdrawn: 2"]  — post 2 is gone, and no reader can tell the loss
  from alice withdrawing it. A writer that loses MUST re-read and fold into what it is served:

  PUT /alice/posts/3                             → 201
  PUT /alice/index         If-Match: "PfbF_ERC…" → 412   lost again
  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "1MhdFwWG…" → 200

  posts 1, 2, 3, verdict ok, notes [] — both devices' work survives.

§8.2 — a number is created once, and numbering need not be gapless

  PUT /alice/posts/4                             → 201   …and now the device crashes

  A reader sees posts 1, 2, 3: a number nobody lists is nothing. The device comes back, and
  it cannot prove it listed 4, so it MUST abandon it:

  PUT /alice/posts/4                             → 409
  PUT /alice/posts/5                             → 201
  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "YzHXzjjV…" → 200

  live numbers 1, 2, 3, 5 — the gap is permanent and costs nobody anything. Listing 4 late is
  the one thing it MUST NOT do, and §7.2 is where that lands:

  PUT /alice/index         If-Match: "xwJhj0uD…" → 200   the hub cannot tell

  the hub stored it; the pinned reader says  host: post 4 is listed now and was not before
  The same check catches a host backdating a post into someone's history.

§8.3 — the post is written before the index that lists it

  PUT /alice/index         If-Match: "xwJhj0uD…" → 200   the index first — the wrong way round

  every reader, until the bytes land:  host: post 6 is listed and not served

  the right way round instead:

  PUT /alice/posts/6                             → 201

  a reader caught between the two writes:  ok, posts 1, 2, 3, 5 — post 6 is not there yet

  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "xwJhj0uD…" → 200

§8.4 — claiming a name: first come, with the profile as the proof

  PUT /bro/profile                               → 200   a second name on the same hub, profile only
  PUT /bro/index                                 → 200   and now one empty index

  read cold, before that empty index:  host: no index served
  read cold, after it:                 ok   — so a publisher MUST write one, even empty

  A hub that accepts writes MUST check the proof. The entity tag is no part of it:

  PUT /alice/profile       If-Match: "eBhjoCAN…" → 403   not signed by the key the chain ends on
  PUT /alice/profile       If-Match: "eBhjoCAN…" → 403   the chain does not walk
  PUT /alice/profile       If-Match: "eBhjoCAN…" → 409   the name is taken, by someone else
  PUT /alice/profile       If-Match: "eBhjoCAN…" → 409   a version that has not advanced
  PUT /alice/index         If-Match: "nU0p2_UG…" → 403   not the key alice's profile ends on

  and the honest case those checks must not break — a rotation, then the index re-signed:

  PUT /alice/profile       If-Match: "eBhjoCAN…" → 200
  PUT /alice/index         If-Match: "nU0p2_UG…" → 403   the rotated-away key no longer signs it
  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "nU0p2_UG…" → 200

  a reader across the rotation: ok, posts 1, 2, 3, 5, 6

§8.5 — a number held by a file that is not the owner's, reclaimed by the owner and nobody else

  PUT /alice/posts/7                             → 201   a stranger: nothing is checked on the ordinary path
  PUT /alice/posts/8                             → 201   a thief holding the key alice rotated away from
  PUT /alice/posts/7                             → 200   declares 7, signed by the key the chain ends on
  PUT /alice/posts/8                             → 200   one PUT reclaims each number he took
  PUT /alice/posts/8                             → 409   and it does not turn around
  PUT /alice/posts/1                             → 409   listed at that number and address: hers
  PUT /alice/posts/1                             → 409   and she cannot overwrite her own

  Posts 1 and 8 were both signed by the anchor key, which is still in the chain. Post 1 is hers
  because the index lists it at that number and address; post 8 was nobody's, because the other half
  of the rule asks for the key the chain *currently* ends on — if any chain key counted, a thief who
  once held one could squat five numbers and hold them forever.

§8.6 — the same rule for media, by the hash instead of the number

  PUT /alice/media/2uj_-m…                       → 400   bytes that do not hash to the name

  …and now assume a hub that checks nothing on the ordinary path let the junk in anyway:

  PUT /alice/media/2uj_-m…                       → 200   replaced by bytes that do hash to it
  PUT /alice/media/2uj_-m…                       → 409   and never the reverse
  PUT /alice/media/2uj_-m…                       → 409   the same bytes twice is a collision, not a write

§8.7 — what a hub MUST do, and the ceiling on what it can do

  GET     /alice/profile   → 200   Access-Control-Allow-Origin: *   exposes ETag
  OPTIONS /alice/index     → 204   Allow-Methods: GET, PUT, OPTIONS   Allow-Headers: If-Match, Content-Type
  served bytes are the stored bytes: true   (examples/no-canonicalization/ owns that rule)

  A hub MAY require a pass, an account, a rate limit, a bill. Here it does the worst it has, and
  overwrites her index in its own store:
    a reader who never met her   host: the index is not signed by the key the profile ends on
    a reader holding a pin       ok ["no index I can verify"], posts 1, 2, 3, 5, 6
  Whatever a hub does, it can never write as you, because it cannot make your signature. The worst
  it can do is refuse you or delete things.

§8.8 — withdrawal removes a line, not a file

  DELETE /alice/posts/2                          → 405   there is no DELETE verb
  GET /alice/index                               → 200
  PUT /alice/index         If-Match: "ZkRuUuox…" → 200
  GET /alice/posts/2                             → 200   the bytes are still there

  a pinned reader:  ok ["withdrawn: 2"]  — the same note the lost race produced in §8.1
  a hub MAY then drop what the current index does not list, after a grace window covering §8.3:
    alice/posts/2, alice/posts/4, alice/posts/7, alice/posts/8, alice/media/2uj_-m…
  and the reader is unmoved: ok, posts 1, 3, 5, 6. An app MUST NOT tell a user that withdrawing
  erased anything — everyone who already read post 2 still holds it; examples/rewrite/ argues it.

Every line above is asserted.
