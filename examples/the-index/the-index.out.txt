§4.2 — an index that does not fold is invalid, and the verdict is `host`

  a number listed twice          [[1,"hURWhg…"],[2,"AkmRbi…"],[2,"i8fWlv…"]]    DOES NOT FOLD
  a withdrawal of nothing        [[1,"hURWhg…"],[9,null]]                       DOES NOT FOLD
  a number below 1               [[0,"hURWhg…"]]                                DOES NOT FOLD
  a media file listed twice      [["fKGh1G…"],["fKGh1G…"]]                      DOES NOT FOLD
  a media withdrawal of nothing  [[1,"hURWhg…"],["fKGh1G…",null]]               DOES NOT FOLD

  served to a reader with no pin   host — the index does not fold
  top has a floor of its own       top is below the highest number issued
  a feed that has issued nothing   top 0, and valid (§4.3, examples/top-and-rumors/)

  `host` names the wrong party, and the spec says so: it verified, so it came from the
  author's own key, not from a misbehaving hub. A fourth reader state was not worth the
  complexity, and an app SHOULD word it as *the files at this address do not make sense*.

§4 — `entries` MUST come first, and that is not canonicalization

  version 1 body   183 bytes
  version 2 body   340 bytes
  shared prefix    161 bytes — every entry of version 1, at the byte it was at
  version 1 ends   ],"version":1,"top":3}
  version 2 tail   179 bytes, so a reader holding version 1 MAY ask for bytes 161– alone:
                   a range request conditioned on the entity tag it holds (If-Range).

  entries last, version 9 → 10, one line appended: shared prefix 11 bytes — everything
  moved, which is why a reader refuses that shape outright: entries is not the first member.

  It buys the range request and nothing else. Nobody re-serializes anything, and a verifier
  that never heard of the rule still checks the signature correctly — §2.3, and
  examples/no-canonicalization/.

§4.6 — the index MUST be signed by the key the chain currently ends on

  the chain                pukq6V… → kAIz_M… → 17Ffa8…   anchor, rotated, restored
  index by the last key    verifies
  index by the middle key  null — a key that is still in the chain

  that index, to a reader with no pin   host — the index is not signed by the key the profile ends on
  that index, to a reader holding one   ok   notes ["recently restored","no index I can verify"]

  The index is what admits posts. If a reader took one from any key in the chain, a thief
  holding a rotated-out key would go on deciding what counts as hers, and a restore would
  take nothing back. Re-signing the index is what a restore actually restores.

  The honest cost is a window: between the two writes a rotation takes, a truthful host
  serves an index signed by a key the profile no longer ends on. §7.2 answers it — an
  unverifiable index is not an accusation, and a reader holding one it verified keeps it.
